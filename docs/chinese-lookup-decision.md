# 汉英查词决策材料（基于真实库实测）

> 目的：为“是否实现汉英查词、做到什么程度”提供可判断的数据，不做方案宣传。
> 数据源：`Flint3/Data/stardict.db`（851,288,064 B，3,402,564 条，ECDICT 结构）。
> 测量环境：Windows / Python 3.13.14 + 内置 SQLite（FTS5 可用）/ 7z 24.x，文件缓存热态；原型索引与脚本在临时目录，未入库。
> 口径说明见文末“测量方法与限制”。所有标“实测”的数字均来自本机本次运行；标“估算”的给出依据。

---

## 0. 结论摘要

- ECDICT 的中文只在 `translation` 里，没有中文词头；99.2% 的记录含中文，中文正文约 **91.2 MiB / 2545 万汉字**，但可直接反查的“词条”没有现成结构，需要构建。
- CSF 当前只索引 `word`/`sw`（英文），`translation` 只是 zstd 块里的正文；**不改格式就无法按中文查**。加中文索引必须把 `CsfFormat.Version` 从 1 升到 2 并让读取器兼容两版，属于高回退风险。
- 实测最合适的路线是**旁挂独立中文索引文件**（不改 CSF、不改 `IWordSource`/`WordQueryService`）：精确+前缀索引 raw **61.6 MiB**、7z 后 **25.0 MiB**；精确 p95 ≤0.07 ms，前缀 p95 ≤3.94 ms。若还要“输入一个字命中词中任意位置”的子串，再加 bigram **29.9 MiB / 7z 17.4 MiB**，候选检索 p95 ≤2.8 ms。
- 原计划推荐的 **FTS5 trigram 对 2 字中文查询无效**：`苹果`、`银行`、`果` 均返回 0，只有 ≥3 字（`苹果树`）可用。这是本轮实测推翻原方案的关键结论。
- 建议：**做，但只做“精确 + 前缀”，不做拼音、不做首版子串、不做简繁转换**；用旁挂索引，按 `collins desc, frq asc` 排序，复用现有 10/40 条上限。若产品不接受新增 25 MiB 分发包，则退化为“仅支持用户自带中文 mdx”（现有代码已可用，零改动）。

## 1. 现状与需求边界

### 1.1 为什么现在只能英查中

- `stardict` 表的可检索键只有 `word`（唯一）与 `sw`（去空格/符号的折叠键），两者都是英文词头；`translation` 是正文列，没有索引。
- CSF 只构建了 `word` 索引与 `sw` 索引；中文正文被 zstd 压缩在 1662 个记录块里，按记录偏移随机读，**无法对 `translation` 做条件过滤**。
- 运行时查询链路：`MainViewModel.MatchWord` → `WordQueryService.MatchAsync` → `EcdictSource.MatchAsync` → `StarDictDataAccess.MatchWord` → 后端前缀查询。中文输入会走同一条英文前缀链路，自然查不到。
- 代码位置：[MainViewModel_Flint.cs](file:///d:/workingfold/Flint/Flint3/ViewModels/MainViewModel_Flint.cs#L74-L131)、[WordQueryService.cs](file:///d:/workingfold/Flint/Flint3.Core/Query/WordQueryService.cs#L50-L62)、[EcdictSource.cs](file:///d:/workingfold/Flint/Flint3.Data/Sources/EcdictSource.cs#L21-L24)、[CsfFormat.cs](file:///d:/workingfold/Flint/Flint3.Data/Csf/CsfFormat.cs#L13-L52)。

### 1.3 CSF 为什么不能直接支持

- CSF 头 256 B，`Version = 1`；读取器对版本做硬校验：`version != CsfFormat.Version` 直接抛“不支持的 CSF 版本”（[CsfReader.cs](file:///d:/workingfold/Flint/Flint3.Data/Csf/CsfReader.cs#L129-L132)）。
- 头里已用到的字段到 offset 200（`OffFileLength`，8 B，止于 208），208~256 只剩约 **48 B**；新增“中文词条索引 + 中文 bigram 索引”需要至少两组 offset/length/rawLength/count（约 56 B），48 B 不够，必须扩头或复用现有目录结构。
- 现有布局是“记录块 → 记录块目录 → word 索引 → sw 索引 → 首键表 → oxford 位图 → tag 表”，没有留给中文索引的段；新增段要改 `CsfWriter` 的写出顺序、`CsfReader` 的校验与寻址、`CsfStarDictBackend` 的查询分支。
- 现有 csf 文件 121,191,594 B（115.58 MiB），构建 25.4 s（C# 单线程）；任何格式变更都要：
  1. `CsfFormat.Version` 升到 2，读取器同时接受 1/2；
  2. 重新生成并重新分卷入库（现有 7z 分卷 99,614,720 B + 21,522,668 B）；
  3. 旧版本客户端无法读取新 csf（向前不兼容）。
- 因此：**把中文索引塞进 CSF = 动已入库格式 + 版本位 + 发布物失效**，回退风险最高。

### 1.4 mdx 词库里的中文能否用于反查

**能，但取决于用户提供的 mdx 是否有中文词头。**

- `MdxIndexDatabase` 建 `words(word, word_lower, record_offset)`，`word_lower = word.ToLowerInvariant()`；中文经 `ToLowerInvariant` 不变，索引可正常存放。
- `MdxSource.QueryAsync` 用 `word_lower = $lower` 精确匹配；`MatchAsync` 用 `[lower, lower + "\uFFFF")` 前缀区间，中文词头可命中其前缀（如 `苹果` 命中 `苹果树`）。
- 仓库现有 fixture 只有英文 `basic.mdx`（3 条）与加密样本，**没有任何中文 mdx**，也没有 mdx 写入器/生成脚本；因此“mdx 中文反查”目前只是能力存在，没有可用数据。
- 限制：只支持精确/前缀，不支持子串；没有 Collins/frq 排序信号；正文由 mdx 记录决定。

## 2. 中文匹配语义的岔路口

| 语义 | 示例 | 与“输入即查”的兼容性 | 需要的索引 | 主要问题 |
|---|---|---|---|---|
| 精确整串 | `苹果` → `apple` | 兼容；但用户少打一个字就无结果 | 排序词条 + 精确查找 | 词条边界由构建规则决定；长短语需保留 |
| 前缀（推荐） | `苹果` → `苹果`/`苹果树`/`苹果汁` | **最兼容**；每敲一个字符收窄 | 排序词条 + 二分 | 结果可达数百，需排序与上限 |
| 子串/LIKE | `果` → `苹果`/`水果` | 对单字输入不现实；2 字起可做 | bigram（2 字）或 trigram（≥3 字） | 单字命中 1.3 万~42 万；trigram 对 2 字无效 |
| 分词后按词 | `苹果电脑` → `苹果` + `电脑` | 长输入有用，短输入无差别 | 分词词典 | 需额外词典与歧义处理；无空格语言边界不稳定 |
| 拼音 | `pingguo` → `苹果` | 不兼容现有“字母前缀”体验 | 拼音→汉字表 + 多音字/分词 | 仓库无拼音数据；需外部数据，歧义高 |

拼音数据现状：全仓库无 `pinyin`/`拼音` 相关实现；ECDICT 的 `phonetic` 是 IPA 音标，不是拼音。要做拼音必须引入外部数据（Unihan `kMandarin`、pypinyin 词表或 CC-CEDICT），并处理多音字与分词，属于独立功能，不建议放进首版。

### 2.1 一条英文词多个中文义项：排序与去重

- 去重键：英文词本身（大小写不敏感）。`WordQueryService.Rank` 已经按 `entry.Word` 去重并保留先出现的源；单源场景下源内也要先聚合，避免同一英文词出现多次。
- 展示：保留该英文词的完整 `translation`（现有详情页行为），不拆成多条；若要做“命中义项高亮”，需要额外保存命中的中文片段，首版可不做。
- 排序：同一英文词多个义项时，取“匹配质量最高”的义项参与排序（精确 > 前缀 > 子串），不需要把每个义项都变成一行。

### 2.2 一个中文词对应多个英文词：排序

建议规则（可用现有字段，无需新数据）：

1. 匹配质量：词条精确 = 0，词条前缀 = 1，子串 = 2；
2. `collins` 降序（有星级优先）；
3. `frq` 升序（数字越小越常用；NULL 视为无穷大）；
4. 英文词长度升序、再按字母序，保证稳定；
5. 截断到 UI 现有上限（主搜索 10，模式/扩展 40）。

实测验证：`苹果` → `apple`（collins=3, frq=2695）排第一；`银行` → `bank`（collins=1, frq=663）；`电脑` → `computer`（collins=4, frq=589）；`一个` → `a`/`one`/`single`（collins=5）。规则与直觉一致。

注意：`WordQueryService.Rank` 是按“英文词 vs 输入串”分精确/前缀/其他组的。中文输入下所有英文词都落在“其他”组，**组内保持源返回顺序**；因此中文匹配质量排序必须在源（`EcdictSource`/中文索引读取器）内完成，不能依赖上层。

## 3. 候选实现路线与代价

所有体积均为“新增文件/新增段”的增量；查询延迟为原型实测（Python mmap / SQLite FTS5，热缓存）。

### 3.1 路线 A：CSF 内嵌中文索引（版本位升级）

| 项 | 实测/估算 |
|---|---|
| 体积增量 | 词条+倒排 **61.6 MiB**；加 bigram **+29.9 MiB**；合计 91.5 MiB（raw）。CSF 用 zstd-12 分块后估算 +55~70 MiB（按 7z 压缩率 40%~60% 推算，**估算**） |
| 构建耗时 | 现有 CSF 构建 25.4 s（C# 实测）；中文词条提取+倒排在 Python 下 47 s，C# 估算 +25~40 s，总构建估算 50~65 s（**估算**） |
| 查询 p50/p95 | 精确 0.02~0.04 / 0.03~0.07 ms；前缀 0.5~3.3 / 0.9~3.9 ms（Python mmap 实测，见 3.2） |
| 改动面 | `CsfFormat`（版本、头字段）、`CsfWriter`、`CsfReader`（双版本）、`CsfStarDictBackend`、CLI 构建、全部 csf 测试与分卷；`IWordSource`/`WordQueryService` 不变 |
| 工作量级 | **L**（格式变更 + 双版本 + 重新生成 115.58 MiB 发布物 + 回归对拍） |
| AOT(L1)/免打包 | 纯托管 + mmap，无新依赖；兼容 |
| 回退风险 | **高**：旧客户端读不了 v2；新客户端必须兼容 v1；发布物体积与分卷数量变化；一旦格式细节有误，所有用户受影响 |

### 3.2 路线 B：旁挂独立中文索引文件（推荐）

新增 `Flint3/Data/stardict.zh.idx`（与 `stardict.csf` 同目录），格式自定、只读 mmap。

| 项 | 实测/估算 |
|---|---|
| 体积增量（精确+前缀） | **61.6 MiB** raw（2,648,701 词条、4,642,415 条倒排）；7z -mx=9 后 **25.0 MiB** |
| 体积增量（子串 bigram） | **29.9 MiB** raw（1,072,880 个 bigram、9,365,272 条倒排）；7z 后 **17.4 MiB** |
| 构建耗时 | Python：词条+倒排提取 47 s，bigram 15.7 s；C# 估算 30~45 s + 10~15 s（**估算**，纯 CPU/IO 线性任务） |
| 查询 p50/p95（50/30 次） | 精确：0.02~0.04 / 0.03~0.07 ms；前缀 `苹果`（432 条）0.52/0.91 ms，`银`（2005 条）3.26/3.94 ms；bigram 候选 `苹果`（775 条）0.29/0.64 ms、`银行`（2061 条）0.76/2.80 ms（未含词条过滤） |
| 改动面 | 新增中文索引读取器（约 300~500 行）+ 构建器（约 200~300 行）+ CLI 命令 + `EcdictSource` 中的中文分支（或 `StarDictDataAccess` 新增内部方法）；`IWordSource`/`WordQueryService`/CSF 格式均不变 |
| 工作量级 | **M** |
| AOT(L1)/免打包 | 纯托管 + `MemoryMappedFile`，与现有 CSF 同模式；无新原生依赖；兼容 |
| 回退风险 | **低**：索引缺失/损坏时 catch 后保持现有英文查询；不影响 SQLite 回退；旧版本客户端忽略新文件 |

补充：
- 词条只存规范中文片段（2~8 字），长短语（>8 字）不进入精确/前缀索引；若产品要求长句反查，需要另行放宽并重估体积。
- 倒排存英文记录 id（与 CSF 记录 id 一致），查询后仍需按 id 读正文，复用现有记录读取路径。
- 可把索引与 csf 一起打进 7z 分卷（新增约 25 MiB 压缩体积，需重新分卷）；也可以做“首次启动可选下载”，避免所有用户被迫增大安装包。

## 4. 风险与坑

1. **中文没有空格，前缀语义必须先定**：`苹果` 作为前缀会命中 `苹果树`、`苹果汁`、`苹果酱` 等 432 个词条；作为精确只命中 64 个英文词。产品需要明确“输入 `苹果` 是想看 apple，还是想看所有以苹果开头的词”。建议默认精确优先、前缀补足。
2. **单字查询必须拒绝或强限制**：`果` 13,645 行、`银` 7,853 行、`人` 140,526 行、`的` 426,474 行。bigram 索引对 1 字输入没有 key；如果放行只能全量扫描词条（Python 原型 4.15 s，C# 估算仍 >100 ms），会破坏输入即查。
3. **trigram 的 2 字盲区**：实测 `苹果`/`银行`/`果` 在 FTS5 trigram 下均为 0，只有 ≥3 字可用。原计划“FTS5 trigram 支持中文子串”对最常见的 2 字词不成立。
4. **简繁差异未测**：ECDICT 以简体为主但混有繁体/异体；不做 OpenCC 之类的映射时，输入繁体可能查不到。映射表会增加体积且需要处理一对多，首版建议明确“仅简体”。
5. **多音字/拼音**：无拼音数据；`phonetic` 是 IPA。拼音输入需要额外数据与分词，且候选歧义大（`xian` → 先/西安/县），不建议首版。
6. **中文标点、全半角**：构建期需做 NFKC、去标点、去 `[域标记]`/括号；否则 `苹果，`、`（苹果）`、全角空格会漏。本轮原型已做前两项，全半角未单独统计。
7. **编码**：db 是 UTF-8；.NET 内部 UTF-16；mdx 支持 UTF-8/UTF-16，GBK mdx 仍不支持（现有已知限制）。含生僻字/扩展 B 区时要注意 UTF-8 4 字节与 `\uFFFF` 前缀上界不覆盖增补平面。
8. **大结果集排序稳定性**：`collins`/`frq` 稀疏（苹果 64 个里仅 1 个有 Collins），大量并列必须用确定性 tie-break（词长、字母序、id），否则每次查询顺序可能变化。
9. **一条英文词最多 708 个规范化中文词条**：若按“词条”出行，单条记录会撑爆列表；必须按英文词聚合。
10. **CSF 格式变更的连锁反应**：版本位、分卷、旧客户端、测试 fixture、`verify` 对拍全部要跟着改；这是路线 A 最大的隐性成本。
11. **冷缓存未测**：与现有 CSF 评估一致，所有延迟均为热缓存；首次查询会触发 mmap 缺页，预计多几十毫秒，未量化。

---

## 5. 明确结论

### 5.1 如果做：推荐路线 B（旁挂索引），最小可用范围如下

- **做**：精确 + 前缀。输入中文时走 `EcdictSource.MatchAsync` 的中文分支；按“精确 > 前缀”再按 `collins desc, frq asc` 排序；沿用现有 10/40 条上限。
- **不做**：拼音、简繁转换、分词、首版子串。
- **索引**：`stardict.zh.idx`，61.6 MiB raw / 25.0 MiB（7z）；缺失或损坏时静默回退英文查询，不阻塞启动。
- **不改**：CSF 格式与版本位、`IWordSource`、`WordQueryService`、`IStarDictBackend` 的公开签名（内部可加方法）。
- **后续可选**：若用户反馈“只记得词中间的字”，再加 bigram（+29.9 MiB raw / 17.4 MiB 压缩，候选检索 p95 ≤2.8 ms）。
- **打包**：与 csf 一起重新分卷（新增约 25 MiB 压缩体积），或在首次启动时按需下载；两种都不影响已安装用户。

理由：在同样满足“输入即查”的路线里，B 的体积最小、查询最快、完全不动已入库格式、回退最简单；C 的 FTS5 对 2 字中文子串无效且体积更大；A 的格式变更风险与发布成本最高；D 依赖用户自备数据，不能作为内置能力。

### 5.2 如果不做：用户失去什么

一句话：**用户在阅读中看到中文时，无法直接查到对应英文，只能先想英文再反查或另开词典；对以“英查中”为主的学习场景可以接受，对写作/翻译式的反向查询是硬缺口。**

如果本轮不做，建议至少做一件低成本的事：在 README/设置页说明“可导入中文-英文 mdx 实现反查”（现有 `MdxSource` 已支持中文词头的精确/前缀），把数据问题交给愿意自备词典的用户，而不是让功能看起来完全不存在。

与 §5.1 的差异：
- 文件名用 `stardict.zhx`（更短，便于与 `stardict.csf` 并排）。
- 索引里不存记录 id 而存全局排名，查询侧归并时无需回读记录即可得到契约顺序，也让排序契约可以被单测固定。

- 子串（bigram）、拼音、简繁转换、分词均未做，与 §5.1 一致。

## 附：测量方法与限制

- **数据**：`Flint3/Data/stardict.db`，851,288,064 B；SQLite 只读查询，未修改库。
- **中文判定**：CJK 统一表意文字 + 扩展 A + 兼容表意文字；不含标点、假名、韩文。
- **词条规范化**：去 `[xxx]` 域标记与 `(...)` 内容；按 `换行 , ， ; ； 、 / |` 切分；去英文词性前缀；取 2~8 字 CJK 连续串；过滤 `网络/地名/医/化/计/经/...` 等高频域标记。该规则是启发式，换规则会改变词条数与体积。
- **原型 B**：Python 3.13 生成排序词条 + delta-varint 倒排，`mmap` 二分查找；p50/p95 为热缓存下 30~50 次重复；构建时间为 Python，C# 预计更快（估算）。
- **原型 C**：Python 内置 SQLite FTS5；`content=''` 仅存索引，rowid 复用 stardict id；构建时间含建表与插入，不含 7z。
- **压缩体积**：`7z a -t7z -mx=9`，仅用于估算分发体积；CSF 实际用 zstd-12，不能直接等同。
- **未测**：冷缓存、C# 端真实延迟、内存峰值、拼音数据、简繁映射、全半角归一化覆盖率、mdx 中文样本。
- **临时产物**：索引原型、FTS 库与脚本在 `%TEMP%\flint-zh\`，未入库。

# 内置词典（stardict.db / ECDICT）存储与瘦身调研

> 范围：只做调研与实测，不改产品代码。文中的原型脚本与基准程序均为临时验证程序（`%TEMP%\flint-star-probe`、`%TEMP%\star-variants`、`%TEMP%\star-bench`；§8 为 `d:\workingfold\Flint\.proto-tmp\`），不入库。
> 测量日期：2026-11-10。机器：Windows，8 逻辑核，32GB 内存，dotnet 10.0.402，源库位于 D:（SSD），变体位于 C: 临时目录。文件缓存为热态，未做冷启动测试。

## 0. 结论速览

1. **812MiB 的文件里，62%（500.9MiB）是索引，其中 268.8MiB 是等价重复**：`word` 在 3 个内容相同的 NOCASE 索引里各存一份（268.1MiB），`id`（本身就是 rowid）还额外建了 2 个等价唯一索引（90.0MiB）。正文（含词头）只占约 224MiB。
2. **只做结构清理**（去掉 2 份重复 `word` 索引、2 份重复 `id` 索引，删掉 6 个全仓库无人读取的列，4KB 页重建）：**811.85 → 479.15MiB（−41.0%）**。精确/前缀/模式查询与峰值内存基本不变（差异在 0.1~0.4ms 与 ±0.2MB 量级，低于阈值），生词本全表扫描反而快 54%（1220→565ms）。运行时只需改一处 SQL 列清单与列映射，无行为变化。
3. **单做 `VACUUM` 不够**：同页大小 1024B 时为 761.97MiB（−6.1%），改 4KB 页后 736.80MiB（−9.2%）。碎片不是主要矛盾。
4. **按记录压缩正文不可行**：ECDICT 绝大多数记录正文只有几十字节，逐条 zstd 帧开销让体积变成原来的 **115%**，brotli 为 **102%**（实测 10 万行样本外推）。
5. **分发用 7z 压缩包**：瘦身库 479MiB → **136.8MiB**（现行原库 7z 是 153.1MiB），解压约 4 秒；仍是"解压即用、免安装"。注意收益有限（下载只降 11%），因为重复索引在压缩时本来就高度可压——**瘦身主要省的是磁盘与 IO，不是下载量**。
6. **换格式（自定义 mmap / 转 mdx）**：估算能到 90~120MiB（词头前编码 + zstd 实测 11.6MiB、正文块压缩估算 40~50MiB、偏移表 10~15MiB），但实现量大、会丢失 `sw` 前缀语义与 `tag`/`oxford` 查询能力，不建议。**（此判断已被 §8 推翻：自定义格式原型实测 148.4MiB 且语义 100% 对齐、AOT 可用，转为推荐；mdx 仍不建议，原因见 §8.4。）**
7. **推荐**：发布管线生成瘦身库（结构清理，零运行时行为变化）+ 需要小下载量时用 7z 包 + 首启解压。**不建议**按记录压缩、自定义格式、仅 VACUUM。**（此条已被 §8 取代：新约束要求常驻磁盘也小、且禁止首启解压成大库，结论改为自定义只读格式 CSF，见 §8.11。）**

## 1. 现状与代码事实

数据文件：`Flint3/Data/stardict.db`，851,288,064 字节（811.85MiB），作为 Content 复制到输出目录，应用以只读方式查询（[StarDictDataAccess.cs](file:///d:/workingfold/Flint/Flint3.Data/StarDictDataAccess.cs)）。

实际读取的列（[StarDictDataAccess.cs](file:///d:/workingfold/Flint/Flint3.Data/StarDictDataAccess.cs#L70-L82) + [StarDictWordItem.cs](file:///d:/workingfold/Flint/Flint3.Data/Models/StarDictWordItem.cs)）：

| 用途 | 列 |
|---|---|
| `select *` 后读取 | `id`、`word`、`sw`、`phonetic`、`definition`、`translation`、`exchange` |
| 仅出现在 WHERE 里 | `tag`（生词本筛选）、`oxford`（牛津标签）、`id`（生词本增量分页） |
| **全仓库无读取点** | `pos`、`collins`、`bnc`、`frq`、`detail`、`audio` |

查询 SQL：

- 精确：`select * from stardict where word = $word`（列 `word` 为 `COLLATE NOCASE`，大小写不敏感）。
- 前缀/联想：`select * from stardict where sw >= $word order by sw, word collate nocase limit $limit`（依赖 `(sw, word)` 索引）。
- 模式：`select * from stardict where word like $pattern [and length(word)=N] order by word collate nocase limit $limit`（`%x` 类走索引有序扫描 + LIMIT 提前终止）。
- 生词本：`tag like '%x%'` / `oxford = 1` 全表扫描 + `order by word`。

Schema（`sqlite_master`）：

```
CREATE TABLE stardict(
  id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL UNIQUE,   -- UNIQUE 产生 autoindex_1（重复）
  word VARCHAR(64) COLLATE NOCASE NOT NULL UNIQUE,        -- UNIQUE 产生 autoindex_2
  sw VARCHAR(64) COLLATE NOCASE NOT NULL,
  phonetic VARCHAR(64), definition TEXT, translation TEXT,
  pos VARCHAR(16), collins INTEGER, oxford INTEGER, tag TEXT,
  bnc INTEGER, frq INTEGER, exchange TEXT, detail TEXT, audio TEXT);
CREATE UNIQUE INDEX stardict_1 ON stardict(id);           -- 与 autoindex_1 完全重复
CREATE UNIQUE INDEX stardict_2 ON stardict(word);         -- 与 autoindex_2 完全重复
CREATE INDEX stardict_3 ON stardict(sw, word collate nocase);
CREATE INDEX sd_1 ON stardict(word collate nocase);       -- 与上面两个 word 索引等价
```

### 2.3 与上游 ECDICT 的关系

- 列集合与 ECDICT 官方 `stardict.db` 一致（`word/phonetic/definition/translation/pos/collins/oxford/tag/bnc/frq/exchange/detail/audio`），`sw` 是上游构建时派生的列。
- 冗余索引、`audio` 全空、`detail` 基本为空，都来自上游构建；`sd_1` 与 `stardict_1..3` 命名不同，疑似后来补建，**未联网核对上游发布包，标注为未确认**。
- 结论：没有"上游有而本库裁掉"的字段；相反，本库带着上游的历史冗余。可以直接在发布管线里做"读上游库 → 建瘦身库"的转换，不需要改上游数据。

## 3. 测量口径

- 每次测量独立进程；内存取 `Process.PeakWorkingSet64`。
- 查询样本：从全库按 id 抽样 400 个真实词条（固定种子 20261110），与具体变体无关。
  - 精确 300 次；前缀 200 次（取词前 4 字符，与产品 `MatchWord` 同 SQL）；模式 60 次（`app%`、`%ing`、`_a_e` 各 20 次，与 `WordPattern` 翻译规则一致）。
- 所有查询都读取整行正文（`select *` 或等价的显式列清单），结果条数 10~20，与产品一致。
- 每次查询新建连接（`Pooling=False;Mode=ReadOnly`），与 `StarDictDataAccess` 行为一致，连接开销计入延迟。
- 首查：新进程内第一条精确查询（含进程启动、JIT、连接建立）。
- 噪声：同一文件重复跑，p50 在 0.2~0.9ms 区间内波动可达 ±50%；后台有压缩任务时整体慢约 1 倍。下文为**安静状态下**的数据；毫秒级差异不应过度解读。

### 4.3 正文压缩（路线 b）实测否决

对 10 万条随机行（按 id 取模），把 `translation+definition+exchange+phonetic` 拼成一条记录后逐条压缩（样本外推全库原始正文 129MiB）：

| 方式 | 压缩后 | 相对原始 |
|---|---|---|
| zstd level 12，逐条独立帧 | 148 MiB | **115%**（变大） |
| brotli quality 5，逐条独立帧 | 132 MiB | **102%**（基本不变） |

原因：ECDICT 的正文中位数只有几十字节，每条 9~13 字节的帧头 + 小块字典效率损失超过了压缩收益。**逐记录压缩在这份数据上没有意义**（与 mdx 每条记录几百字节到几 KB 的情况不同）。若要做，只能"大块压缩 + 行内偏移"（相当于自定义格式），见 4.4。

词头前编码（公共前缀 + 后缀）后整体 zstd-12：3,402,564 条，前编码 29.0MiB → **11.6MiB**（词头本身 51.4MiB）。

### 4.4 换格式（路线 e）估算

- 词头 + 前缀键：前编码 + zstd ≈ 11.6MiB（实测）；`sw` 派生索引需要额外顺序映射，约 +8~12MiB。
- 正文（124.7MiB）按 256KB~1MB 大块 zstd：按整库 7z 的 5.3:1 与逐列可压性估 2.5~3:1 → 40~50MiB（**估算，未单独实测**）。
- 3.4M 条的偏移/长度表：原始 27MiB，varint/增量编码后约 10~15MiB。
- 合计 **约 70~90MiB**，比瘦身库再小 80% 左右，接近 7z 包大小；但等于重写一套存储与查询层。
- 转 mdx：mdx 用 64KB 块 zlib，正文压缩率与上述块压缩同量级；但 mdx 键按字节序排序，无法直接做大小写不敏感/`sw` 语义查询（见 [mdx-storage-analysis.md](file:///d:/workingfold/Flint/docs/mdx-storage-analysis.md) 的 B 路线实测：精确失配 43%），仍需 sidecar 索引（3.4M 条 SQLite 索引约 100MiB，或 zstd 索引约 20MiB），且要额外转换与导入步骤。

### 4.5 发布形态（路线 d）实测

- 解压耗时：现有原库 7z（153.1MiB → 851MiB）**4.2s**；瘦身库 7z（136.8MiB → 479MiB）**4.2s**（7z CLI，热缓存）。
- 首次运行磁盘峰值：压缩包 + 解压后库 = 137 + 479 ≈ **616MiB**；若解压到 `%LOCALAPPDATA%\Flint3\FlintData`，与现有 mdx 数据目录一致，**不需要管理员权限**，不写注册表。
- 若用 .NET 内置 `ZipArchive`（deflate）避免依赖 7z 可执行文件：包体 154.0MiB（实测 7z 的 deflate；.NET 实现数值接近），解压 2~4s。

## 5. 阈值与判定

以下是**建议阈值**（括号内为当前基线），属于产品决策，可按发布渠道调整：

| 编号 | 指标 | 建议阈值 | 依据 |
|---|---|---|---|
| T1 | 分发体积（单次下载） | ≤ 150 MiB | 现有 7z 开发包 153MiB，不应更差 |
| T2 | 首次可用（含首启解压） | ≤ 15 s；日常首查 ≤ 1 s | 一次性成本；基线首查 74~104ms |
| T3 | 精确 p95 | ≤ 1.5 ms | 不低于现有体验 |
| T4 | 前缀 p95 | ≤ 5 ms | 输入联想需即时 |
| T5 | 模式 p95 | ≤ 100 ms | 用户显式触发 |
| T6 | 生词本计数（全表扫描） | ≤ 10 s | 基线 1220ms，允许劣化但需可控 |
| T7 | 导入/构建峰值内存 | ≤ 200 MB | 桌面应用可接受 |
| T8 | 查询峰值工作集 | ≤ 200 MB | 基线 44MB |
| T9 | 便携性 | 解压即用、免安装、不写注册表、无额外运行时、免管理员权限 | 现有分发契约 |

|---|---|---|---|---|---|---|---|---|
| A 现状 | **不通过 812MiB** | 通过 | 通过 | 通过 | 通过 | 通过 | 通过 | 不通过（体积） |
| B1 仅 VACUUM | **不通过 762MiB** | 通过 | 通过 1.43 | 通过 3.62 | 通过 8.11 | 通过 | 通过 | 不通过（收益不足） |

说明：

- 单纯 `VACUUM` 或改页大小都达不到体积目标，且 B2 的前缀 p95 实测 7.06ms 超过建议阈值（不同文件/页大小下的 B 系列数值波动较大，结论是"收益不足"，不是"一定变慢"）。
- C 在磁盘体积上仍未过 T1，但它是**唯一零行为变化**的结构性收益；配合 7z 后 T1 才达标。
- 逐记录 zstd 直接让文件变大，无需再讨论延迟。

## 6. 结论与建议

### 6.1 推荐路线

**第一步（建议做，低风险）：发布管线生成瘦身库。**
- 表：`id INTEGER PRIMARY KEY`（去掉 `UNIQUE`/`AUTOINCREMENT`，让它回归 rowid 别名）、保留 `word`（NOCASE）、`sw`、`phonetic`、`definition`、`translation`、`tag`、`oxford`、`exchange`；删除 `pos/collins/bnc/frq/detail/audio`。
- 索引只保留两个：`(word COLLATE NOCASE)` 与 `(sw, word COLLATE NOCASE)`。
- 页大小 4096；构建用 `PRAGMA journal_mode=OFF; synchronous=OFF`（一次性离线转换）。
- 结果：479.15MiB（−41.0%），精确/前缀/模式延迟与内存无实质变化，生词本全表扫描快约 54%。
- 运行时改动：`StarDictDataAccess` 的 `select *` 改为显式列清单（`id, word, sw, phonetic, definition, translation, exchange`），`ReadWordItem` 的列序号相应调整（`exchange` 从 12 变为 6）；SQL 与查询语义不变。改动面：1 个文件 + 测试 fixture 的建表语句。
- 发布管线：在现有 `tools/prepare-data.ps1` 之后增加一步"瘦身转换"（Python 或一个小 C# 工具，本机 10 秒内），或直接提交瘦身后的 7z。**不要把 479MiB 的 db 提交进 git**。

**第二步（按需）：小体积分发。**
- 若下载体积是硬指标：发布 7z（136.8MiB）+ 首启解压到 `%LOCALAPPDATA%\Flint3\FlintData\stardict.db`，解压约 4s，峰值磁盘约 616MiB，免管理员权限；运行时需把 `DatabasePath` 从 `AppContext.BaseDirectory/Data` 改为"优先用已解压文件，否则从包内解压"。
- 若可以接受 479MiB 的下载：直接把瘦身库放进发布 zip，运行时零改动。这是"最少改动"的方案。

| 路线 | 改动点 | 工作量级 |
|---|---|---|

| C 瘦身库 | 一次性转换脚本 + `StarDictDataAccess` 列清单/映射 + 测试 fixture 建表 | 1~2 人日 |

### 6.3 不建议做的部分

1. **仅 `VACUUM` 或改页大小**：−6~9%，达不到目标，且要付出 30~40s 的构建成本。
2. **逐记录 zstd/brotli 压缩正文**：实测体积反而 +15%/+2%，因为 ECDICT 的记录太短，帧开销无法摊薄。
3. **自定义 mmap 格式 / 转 mdx**：体积能再降到 70~120MiB，但要重写查询层、索引与容错，并丢失 `sw` 前缀语义（`MatchWord` 的"最近匹配"排序）和 `tag`/`oxford` 的 SQL 过滤能力；收益（相对瘦身库再省 350~400MiB 磁盘）与风险不匹配。若未来要支持"超大规模词库/自定义词典"，再作为独立项目评估。
4. **`idx_sw` 去掉 `word` 列**（可再省约 65MiB）：全库有 **199,037 组** `sw` 冲突，去掉后同一 `sw` 组内的排序由 `word` 变为 rowid，会改变联想结果顺序，属于行为变化，不建议顺手做。
5. **`WITHOUT ROWID` 聚簇到 `word`**（可再省约 78MiB 的 `idx_word_nocase`）：会失去 rowid，生词本 `id > $lastId` 的增量分页语义需要重写，且要额外索引维持 `id` 顺序，净收益有限，不建议在本次范围内做。
6. **把 `sw` 从表里删掉只留索引**：SQLite 不支持"索引引用已删除列"，表达式索引又无法表达 `strip()` 语义，做不到。

### 6.4 对 AOT(L1)/免打包/R2R 的影响

| 方案 | 影响 |
|---|---|
| 只换数据文件（瘦身库） | **零影响**：发布仍是自包含 + R2R + AOT L1，代码结构不变 |
| 瘦身库 + 7z 首启解压 | 新增一段 BCL 解压代码（`ZipFile`/`ZipArchive` 或 brotli，纯托管、AOT 安全、无反射），数据目录改到已可写的 `%LOCALAPPDATA%`；不影响裁剪/AOT 配置 |
| 自定义 mmap 格式 | 新增纯托管解析器（需避免反射/序列化），AOT 可行但工作量大、格式演进与损坏恢复需自建 |

### 6.5 一句话回答

**能瘦身，而且主要不是靠"压缩"，是靠去掉 268.8MiB 的重复索引和 6 个无用列：瘦身后 479MiB（−41%），查询不变；分发用 7z 后下载 137MiB。瘦身后仍是"解压即用、免安装、无额外运行时"的便携形态；若接受首启解压，便携性不变，只是首次启动多约 4 秒、临时多占约 616MiB 磁盘。**

## 8.3 路线 1（推荐）：自定义只读格式 CSF

### 8.3.1 格式设计

单文件、纯只读、`MemoryMappedFile`（`MemoryMappedFileAccess.Read`）映射，零落地副作用：

```
[256B header]
  magic "CSF1" | recordsPerBlock | recordCount
  recDirOff | wordDirOff | swDirOff | flagsOff | tagDirOff
[记录块目录]   16B/块：uint64 offset + uint32 len + uint32 crc32(xxHash32)
[记录块数据]   每块 2048 条；块内 = varint 长度表 + 拼接正文
               （phonetic/definition/translation/exchange，zstd-12 整块压缩）
[词头索引目录] 每块 2048 键：firstKey + offset/len
[词头索引数据] 块内 = 公共前缀编码 + varint 后缀长度 + 后缀，整块 zstd
[sw 索引目录/数据] 同上（派生的 sw，按折叠后字节序）
[flags]        3.4M × 1bit：oxford
[tag 目录/数据] tag → 位图（生词本按标签全量筛，无需扫正文）
```

要点：

- **NOCASE 语义**：只折叠 ASCII `A-Z`，排序键 = 折叠后 UTF-8 字节序。这与 SQLite `COLLATE NOCASE` 完全一致，也是它比 mdx（按原始字节序）更适合本产品的根本原因。
- **`sw` 不存副本**：全库 3,402,564 行实测 `sw == ''.join(c for c in word.lower() if c.isalnum())` **0 失配**，可在索引构建期算一次，查询期由词头反推，不必存 `sw` 文本。
- **生词本不扫正文**：`tag`/`oxford` 预计算成位图，计数与前 N 条都是位图遍历 + 按序取记录，把 SQLite 的 1.6s 全表扫描变成毫秒级。
- 块级 xxHash32 用于截断/损坏检测；目录项即可定位，无需读全文。

### 8.3.2 体积构成（实测）

| 部分 | 体积 |
|---|---|
| 记录块（3.4M 条 × 4 字段，zstd-12） | 90.2 MiB |
| 词头索引（前缀编码 + zstd） | 21.98 MiB |
| `sw` 索引（前缀编码 + zstd） | 36.14 MiB |
| flags + tag 位图 | ≈ 0.1 MiB |
| header + 目录 | < 0.2 MiB |
| **合计（单文件）** | **155,610,009 B = 148.4 MiB** |

构建耗时 **90s**（单线程 Python，含读 SQLite、zstd-12、写块），可离线跑在发布管线里，不影响运行时。

### 8.3.3 查询与内存（AOT，D: 同盘）

| 指标 | 实测 | 阈值 | 判定 |
|---|---|---|---|
| 打开（mmap + 读 header/目录） | 4 ms | ≤5s | 通过 |
| 精确 p50/p95 | **0.50 / 1.39 ms** | ≤5ms | 通过 |
| 前缀 p50/p95 | **0.65 / 1.75 ms** | ≤10ms | 通过 |
| 模式 p50/p95 | **3.15 / 37.59 ms** | ≤100ms | 通过 |
| 生词本计数（`%zk%`） | 1.4 ms | ≤2s | 通过 |
| 生词本前 50 条 | 20.4 ms | ≤2s | 通过 |
| `oxford=1` 前 50 条 | 5.6 ms | ≤2s | 通过 |
| 峰值工作集 | **98.1 MB** | ≤200MB | 通过 |

同盘 AOT 对照（同一二进制、同样本）：

| 指标 | SQLite 原库 | CSF | CSF 相对 |
|---|---|---|---|
| 精确 p50/p95 | 1.55 / 4.49 | 0.50 / 1.39 | **快 2~3×** |
| 前缀 p50/p95 | 1.69 / 4.65 | 0.65 / 1.75 | **快 2.6×** |
| 模式 p50/p95 | 3.2 / 8~10 | 3.15 / 37.59 | p50 持平，p95 差 4× |
| 生词本计数 | 1618~1730 ms | 1.4 ms | **快 1000×** |
| 生词本前 50 条 | 79~85 ms | 20.4 ms | 快 4× |
| `oxford` 前 50 条 | 35~37 ms | 5.6 ms | 快 6× |
| 峰值工作集 | 21.3 MB | 98.1 MB | **高 4.6×** |

模式查询 p95 变差的原因：CSF 按词头序扫块并逐条做 LIKE，最坏情况（`%ing` 命中稀疏）要扫完 20 条上限前的多个块；SQLite 用 `word` 索引有序扫描 + LIMIT 提前终止，末端命中更省。37.59ms 仍在 100ms 阈值内，但如果产品对模式查询有更严要求，需要给 `%suffix` 加后缀索引（见 8.3.5 风险）。

峰值 98.1MB 来自块缓存：`_recordCacheLimit = max(4, 8MiB / 单块原始字节)`，加上 8 块 LRU 的解压缓冲与索引块缓存。仍远低于 200MB 阈值。

### 8.3.4 参数敏感性（单次测量，供取舍）

把记录块从 145KB 拉到 ~1MB、zstd 提到 level 15、并且不存 `sw`：

- 体积 **127.37 MiB**（−21MiB）；
- 精确 p95 从 ~1.4ms 升到 **~5.5ms**（刚好卡在 T4 边界）；
- 峰值内存**接近翻倍**（单块解压缓冲变大）。

结论：**块大小不要超过 256KB**。体积收益远小于延迟代价，默认取 128~256KB / 2048 条、zstd-12。

## 8.4 路线 2：直接打包成 mdx（复用 `MdxReader`）

| 项 | 实测/评估 |
|---|---|
| 分发体积 | **93.67 MiB**（正文 180.88MB + 键 49.05MB，64KB 块 zlib） |
| 常驻磁盘 | 93.67 MiB（单文件，满足 T2） |
| 首次可用 | 打开 **4 ms** |
| 精确查询 | 语义**不等价**：mdx 键按原始 UTF-8 字节序，`A` 与 `a` 相距 32 位；实测与 SQLite 结果**失配 43%**（§4.4 已记） |
| 前缀/联想 | `sw` 语义不存在于 mdx；若用原键前缀，大小写与去符号规则都不对 |
| 模式 | mdx 无 `LIKE` 能力，只能全键扫描 |
| 生词本 | `tag`/`oxford` 不在 mdx 模型内，需侧车 |
| 补救后体积 | 加 CSF 侧车索引（词头 + sw + flags）≈ 93.67 + 58.1 = **151.8 MiB**，反而**大于纯 CSF 148.4MiB** |
| 工作量 | 低（复用 `MdxReader` + 转换脚本，3~5 人日），但**语义改造的补丁量抵消了省下的工作量** |
| 判定 | **不通过**（T4/T5/T7 语义不达标；补救后 T1 也失守） |

这是本节最值得强调的结论：mdx 体积最小（93.67MiB），但**它的排序语义与本产品的 NOCASE / `sw` 语义不兼容**，不是"压缩率更高"就能补的。只有当产品愿意放弃大小写不敏感与联想排序时才能用。

## 8.5 路线 3：Parquet（zstd，row group 随机访问）

| 项 | 实测/评估 |
|---|---|
| 分发体积 | **97.03 MiB**（zstd-9，65536 行/row group，共 52 组） |
| 常驻磁盘 | 97.03 MiB（满足 T2） |
| 首次可用 | Python/pyarrow 打开即用；**.NET 侧未测** |
| 精确查询 | **11.29 ms**（pyarrow，含解压整个 row group 65536 行） |
| 前缀/模式 | **无索引**：只能整列扫描或整组解压，`LIKE` 无下推 |
| 生词本 | 列扫可做，但每次都要解压整组，`tag like '%x%'` 不优于 SQLite |
| 工作量 | 中（引入 Parquet 库；.NET 侧需 Parquet.Net，AOT/裁剪状态未验证），5~8 人日 |
| 判定 | **不通过**（T4 精确 11.29ms > 5ms；T5/T6 无索引；AOT 未验证） |

Parquet 是**分析型列存**，不是点查格式：row group 内必须整组解压，点查延迟由 row group 大小决定（64K 行 ≈ 11ms）。把 row group 缩到 1K 行能压到 ~0.5ms 但体积会明显变大、且 3400 个 row group 的元数据开销上升。即便调参，也仍缺前缀/模式索引。

## 8.6 路线 4：LMDB / 其他嵌入式 KV

| 项 | LMDB 实测/评估 |
|---|---|
| 分发体积 | 无内建压缩；`map_size` 2GB **稀疏预分配**，逻辑上就是 2GB |
| 常驻磁盘 | **673.23 MiB**（`last_pgno=172346` × 4KB，实测），比瘦身 SQLite 还大 |
| 首次可用 | 打开快（mmap），但未测延迟 |
| 精确 | 预期 ~0.1ms（B+tree 点查，mmap） |
| 前缀 | 可用 `MDB_SET_RANGE` 做有序扫描；但 NOCASE 需自建折叠键（等于再存一份键） |
| 模式 | 无 LIKE，只能全扫 |

| AOT | .NET 绑定（`LMDB.NET` 等）多为 P/Invoke 原生库，**与"单文件 AOT 免打包"冲突**，需额外携带 `lmdb.dll` |
| 判定 | **不通过**（T2 673MiB；T9 需额外原生库） |

其他嵌入式 KV（简述，未逐一实测）：

- **RocksDB / LevelDB**：LSM，自带 Snappy/zstd 块压缩，写入友好；但目录多文件、后台 compaction 线程、原生库依赖，便携性与 AOT 都差。适合写入密集，不适合只读词库。
- **LiteDB**：纯托管 + 单文件，AOT 友好；但它是 BSON 文档库、无内建块压缩，3.4M 条正文基本等于裸存（预估 300MB+），且点查性能弱于 SQLite。不实测即可排除。
- **SQLite + `WITHOUT ROWID` + 页压缩扩展**：官方无页压缩；第三方 `sqlite3-zstd` 需替换引擎，与 `e_sqlite3.dll` 的 AOT/免打包约束冲突。

## 8.7 路线 5：继续用 SQLite，但正文按块压缩

即"表只存索引与块号，正文按 2048 条一块 zstd 存 BLOB"，对照 §4.3 被否决的"逐记录压缩"。

Schema（`build_sqlite_chunk.py`）：

```sql
CREATE TABLE chunk(id INTEGER PRIMARY KEY, data BLOB NOT NULL);
CREATE TABLE entry(word TEXT PRIMARY KEY COLLATE NOCASE,
                   ord INTEGER NOT NULL,
                   sw TEXT NOT NULL COLLATE NOCASE,
                   tag TEXT, oxford INTEGER NOT NULL) WITHOUT ROWID;
CREATE INDEX idx_sw ON entry(sw, word);
```

| 指标 | 实测 | 阈值 | 判定 |
|---|---|---|---|
| 正文块（压缩后） | 56.85 MB | — | 逐记录压缩是 115%，**按块压缩收益显著** |
| 库文件 | **325.09 MiB** | ≤200MiB | **不通过 T2** |
| 构建耗时 | 54.5 s | — | — |
| 精确 p50/p95 | 0.98 / 2.05 ms | ≤5ms | 通过 |
| 前缀 p50/p95 | 1.24 / 2.90 ms | ≤10ms | 通过 |
| 模式 p50/p95 | 1.45 / 5.81 ms | ≤100ms | 通过 |
| 生词本计数 | 583~622 ms | ≤2s | 通过 |
| 峰值工作集 | 27.4 MB | ≤200MB | 通过 |

**结论：按块压缩确实解决了"逐记录压缩反而变大"的问题（正文 125MB → 56.85MB），但救不了总量。** 325.09MiB 里 **268.2MiB 是 `entry` 表与 `idx_sw` 索引**——SQLite 的 b-tree 索引不可压缩，索引成了天花板。要压到 200MiB 以下，只能再删索引，而删索引就回到"没有前缀/模式查询能力"。

这是"继续用 SQLite"这条路线的硬上限：**正文只占 17%，压到极致也省不出量。**

## 8.8 路线 6：混合方案

| 变体 | 设计 | 体积 | 判定 |
|---|---|---|---|
| 6a | 词头/sw 索引 zstd 存文件 + 正文块 zstd + mmap 只读 | **148.4 MiB**（就是 CSF，索引与正文都在同一 mmap 文件里） | **通过** |
| 6b | 词头索引放 SQLite（不可压）+ 正文块压缩 | 325.09 MiB | 不通过（同 8.7） |
| 6c | mdx 存正文 + CSF 侧车存索引 | 151.8 MiB | 不通过（T1 超线，且两套格式对齐成本更高） |

"混合"在本产品上没有额外收益：**索引如果能压，就必须离开 SQLite 的 b-tree；一旦离开，正文也没必要留在 SQLite**。6a 是唯一自洽的组合，而它正是路线 1。

## 8.11 推荐路线与实施参数

**推荐：路线 1 自定义只读格式 CSF（单文件 + mmap + 按块 zstd）。**

理由：

1. **唯一同时满足分发 ≤150MiB 与常驻 ≤200MiB 的路线**（148.4MiB，两个指标是同一个数）。
2. **查询语义 100% 对齐**：NOCASE 折叠 + `sw` 派生规则全库 0 失配，精确/前缀/模式/生词本逐条比对全等（300/200/3 + tagCount）。
3. **延迟不劣化，部分显著更优**：精确/前缀快 2~3×，生词本快 3 个数量级（位图替代全表扫描）。
4. **AOT 已验证**：纯托管依赖，5.4MiB 单文件产物，实测跑通全部查询。
5. **便携性最好**：一个只读文件，无注册表、无管理员、无额外运行时、无首启展开。

实施参数（建议写进构建器）：

- 记录：2048 条/块、目标块 128~256KB（此前 145KB 一档实测最优；1MB 会顶到 T4 边界）、zstd-12（level 15 收益 ~5% 但更慢）。
- 索引：2048 键/块、块内公共前缀编码、整块 zstd、目录项 `firstKey + offset + len`。
- 每块 xxHash32 校验；header 带版本号与 `recordCount`，便于校验截断。
- 词头/sw 索引键统一按"折叠后 UTF-8 字节序"排序；`sw` 不入库，查询期由 `word` 派生。
- `tag`/`oxford` 独立位图区，生词本不触正文。
- 块缓存上限 8MiB（约 8 块），LRU。

迁移路径：保留 `StarDictDataAccess` 的公开签名不变，内部改调 `CsfReader`；构建器与 `docs` 里的校验脚本作为发布管线的一步；上线前用 `verify` 模式跑全量（至少 300 精确 / 200 前缀 / 3 模式 / tagCount）做回归门禁。

## 8.12 不建议的路线及数据支撑

1. **mdx 直接用（93.67MiB）** —— 体积最小，但键按原始字节序，与 NOCASE 语义失配 **43%**；`sw` 与 `tag`/`oxford` 不在 mdx 模型内。补侧车后 151.8MiB，比 CSF 更大。**不建议**。
2. **Parquet（97.03MiB）** —— 精确点查 **11.29ms**（超 T4 两倍），无前缀/模式索引，.NET+AOT 未验证。列存不是点查格式。**不建议**。
3. **LMDB（673.23MiB）** —— 无内建压缩、`map_size` 稀疏预分配、需原生 `lmdb.dll`，与"单文件 AOT 免打包"直接冲突，体积还大于瘦身 SQLite。**不建议**。
4. **SQLite + 正文块压缩（325.09MiB）** —— 按块压缩本身有效（正文 125MB→56.85MB，对比逐记录 115%），但 268.2MiB 是 b-tree 索引，不可压。压到 200MiB 以下只能删索引，等于放弃查询能力。**不建议**。
5. **回到"瘦身库 + 7z 首启解压"（§5 的旧推荐）** —— 首启要摊开 479MiB，违反新约束 T2/T2′。**已被本节取代**。
6. **只做页面/参数微调（VACUUM、页大小、块大小加大）** —— 体积最多再降 20MiB 量级，代价是延迟顶到阈值边界与内存翻倍（见 8.3.4）。**收益与风险不匹配**。

## 8.13 未测与限制

- **未实现 FST / 双数组 trie / 排序词头 + 分块前缀索引**：CSF 实际用的是"词头分块 + 块内前缀编码 + 目录二分"。FST 能把词头索引从 21.98MiB 再压到 ~8MiB，但 .NET 侧无成熟 AOT 友好的 FST 实现，且要自建序列化，本节未做，**体积数据以 CSF 实测为准，FST 的可能收益为估算**。
- **Parquet 的 .NET 侧与 AOT 未测**：11.29ms 是 pyarrow 数值（含整 row group 读取），Parquet.Net 可能不同；未验证不代表一定更差，但在缺索引这点上不会改变结论。
- **LMDB 延迟未测**：只测了体积（673.23MiB）与映射/预分配行为；即使延迟优秀，T2 与 T9 也已否决。
- **CSF 冷缓存未测**：所有数据为文件缓存热态；mmap 在冷盘下首查会触发缺页，预计首屏多几十毫秒，未量化。
- **模式查询 p95 抖动大**（35~57ms 区间，取决于 `%suffix` 命中密度），单次测量；37.59ms 是安静状态下的一次取值。若产品要求更严，需加后缀索引。
- **构建耗时**（CSF 90s / 分块库 54.5s）为单线程 Python，未做并行优化；只影响发布管线，不影响运行时。
- `%TEMP%` 下的早期原型产物已被系统清理（两次），本节数据来自工作区 `d:\workingfold\Flint\.proto-tmp\` 下的重建产物；该目录验证完即删，不入库。
- 生词本基线 1618~1730ms 取自 AOT 二进制的 `star` 模式（`Microsoft.Data.Sqlite`），与 §4.2 的 Python 1220ms 不同源，**不可直接相减**；本节只用来对照 CSF 的 1.4ms。

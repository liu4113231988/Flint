# 大词典（mdx）存储与性能调研

> 范围：只做调研与实测，不改产品代码。文中的"原型"均为临时验证程序（位于 `%TEMP%\flint-mdx-probe`，不入库），不代表最终实现质量。
> 测量日期：2026-11-10。机器：Windows，8 逻辑核，32GB 内存，dotnet 10.0.402。文件缓存为热态（同一文件重复读取，未做冷启动/清缓存测试）。

## 0. 结论速览

1. **前提需要修正**：当前 sidecar 索引里**没有词条正文**。索引只有 `word / word_lower / record_offset / record_size`，正文一直是查询时从 mdx 的压缩块里按偏移解压的。所谓"索引与文本 1:1"来自上一轮样本的特殊构造（词条正文只有几十字节、单词却有 15 字符），不是普遍规律。
2. **索引体积的真正驱动因素是"词头数量 × 词头长度"**，与正文长短无关；而且当前实现把词头存了 3 份（`word`、`word_lower`、`word_lower` 的二级索引），外加一个查询从不使用的 `record_size` 列。
3. 1M 词条实测（正文 84.4MB 简明 / 760.7MB 富文本，mdx 29.7/129.3MB）：
   - 现方案索引 **50.6~51.6MB**（简明词典下是 mdx 的 1.7 倍）；
   - 仅改 SQLite schema（`WITHOUT ROWID` + 复合主键、删 `record_size`）可降到 **30.8MB（−40%）**，查询延迟与内存持平；
   - 自建 zstd 分块索引可降到 **5.6~6.1MB（−88%）**，精确/前缀更快，模式查询慢约 3 倍但绝对值 <60ms；
   - 直接使用 mdx 自带键索引（零额外存储）**语义不等价**：mdx 键按字节序排序，大小写不敏感查询无法通过二分定位（校验中 300 个精确查询失配 131 个），不作为可选主路线。
4. **已落地（2026-11-10）**：只做了 SQLite schema 优化（低成本、无行为变化）；1M 词条索引 51.55 → 30.80MB（−40%），延迟/内存持平，详见第 8 节。如果后续产品要求"索引远小于 mdx"，再评估 zstd 分块索引。

## 1. 现状与代码事实

- 导入流程（调研时的旧结构，已于 2026-11-10 改为第 8 节的精简结构）：复制 mdx 到 `%LOCALAPPDATA%\Flint3\FlintData\Dicts\{id}.mdx`，顺序遍历 mdx 键块，向 `{id}.db` 写入 `words(word, word_lower, record_offset, record_size)`，随后建 `idx_words_lower` 索引（[MdxIndexDatabase.cs](file:///d:/workingfold/Flint/Flint3.Data/Mdx/MdxIndexDatabase.cs)）。
- 查询：按 `word_lower` 等值/区间/`LIKE` 命中索引，拿到 `record_offset` 后调用 `MdxReader.ReadRecord` 解压所属记录块并抽取纯文本（[MdxSource.cs](file:///d:/workingfold/Flint/Flint3.Data/Mdx/MdxSource.cs#L29-L85)）。
- `record_size` 只在插入时写入，**全仓库没有任何读取点**（`grep record_size` 仅命中建表和插入两处）。
- 调研时索引文件没有 schema 版本标记（换 schema 后旧索引不会自动重建）；该问题已随 C 方案落地解决（`user_version`，见第 8 节）。

## 2. 样本构造

数据源：仓库内 `Flint3/Data/stardict.db`（ECDICT，340 万词条）。用 `word not glob '*[^A-Za-z]*' and length(word) >= 3` 过滤出 112 万纯字母词头，取前 100 万条构造两种口径：

| 样本 | 词条数 | 未压缩正文 | 词头文本 | mdx | 平均正文 | 压缩比（正文/mdx） |
|---|---|---|---|---|---|---|
| `bench1m_real`（富文本） | 1,000,000 | 760.72 MB | 9.75 MB | 129.28 MB | 797.7 B | 5.9 : 1 |
| `bench1m_compact`（简明） | 1,000,000 | 84.43 MB | 9.75 MB | 29.73 MB | 88.5 B | 2.8 : 1 |

- 富文本样本每个词条包含：`data-hw` 属性的 `<div>`、`<h2>` 词头、音标、1~3 个义项（随机词性 + 真实译文）、英文释义、**2~6 条随机例句**（8 种句式模板 × 随机名词/形容词/动词/年份/来源）、随机出现的词形变化/近义词/参见链接/来源行。随机数种子固定（20261110），正文具有真实词典的长尾与不重复性，不是可被高度压缩的重复文本。
- 简明样本复用同一批词头，正文为"词头 + 音标 + 中文译文 + 80 字节内英文释义"，用来覆盖"正文很短、索引占主导"的真实词典类型（例如简明英汉）。
- mdx 由 `writemdict`（Python）写出，UTF-8、zlib 压缩、块大小 64KB、未加密，属于当前实现支持的范围。
- 生成脚本为临时文件：`%TEMP%\mdxgen\gen_big.py`（`--compact` 切换口径），未入库。

## 3. 测量口径

- 每次测量独立进程，避免上一路线残留的堆/句柄影响内存峰值；内存取 `Process.PeakWorkingSet64`。
- 查询样本：从 mdx 全量词条做**蓄水池抽样** 400 个词（种子 20261110），保证与索引实现无关。
  - 精确：300 次，结果上限 20；
  - 前缀：取样本词前 4 个字符，200 次，上限 10；
  - 模式：`app*`、`*ing`、`?a?e` 各 20 次，共 60 次，上限 20。
- **所有路线的查询延迟都包含"读记录正文"**（与现实现一致：命中后从 mdx 解压记录块并抽取文本）。
- SQLite 路线每次查询新建连接（`Pooling=False`），与当前 `MdxSource` 行为一致，连接建立开销计入延迟。
- 导入耗时：现方案取 `MdxDictionaryStore.ImportAsync` 端到端（SHA1 + 复制 + 建索引），其余路线为"复制 + 建索引"中的建索引部分（复制/哈希约 0.5~0.9s，可线性叠加）。
- 延迟为同一进程内、文件缓存已热的重复测量，取 p50/p95/max。**同一变体重复跑，p95 波动约 ±20%**（例如 `cur2` 模式查询 p95 在 13.5~18.5ms 之间），不要把毫秒级差异当成路线差异。

## 4. 实测结果

### 4.1 现方案（A：不压缩）

| 样本 | 导入 | mdx | 索引 | 合计占用 | 首查 | 精确 p50/p95 | 前缀 p50/p95 | 模式 p50/p95 | 峰值工作集 |
|---|---|---|---|---|---|---|---|---|---|
| 富文本 1M | 3545 ms | 129.28 MB | **51.55 MB** | 180.82 MB | 15.72 ms | 0.54 / 1.01 | 1.05 / 2.21 | 8.05 / 15.71 | 62.0 MB |
| 简明 1M | 3164 ms | 29.73 MB | **50.63 MB** | 80.36 MB | 16.16 ms | 0.55 / 0.99 | 0.90 / 1.98 | 8.24 / 16.05 | 59.4 MB |

结论：延迟与内存都没问题；**问题是索引绝对值**——简明词典下索引是 mdx 的 1.70 倍，富文本下是 0.40 倍。

### 4.2 索引体积构成（为什么是 51MB）

用"逐个删除冗余"的变体差值测得（富文本样本，词头集合与简明样本完全相同，因此体积一致）：

| 组成 | 体积 | 测量方式 |
|---|---|---|
| `word_lower` + `record_offset`（主键，无冗余） | 20.11 MB | `lower` 变体（20.11MB） |
| 原始大小写 `word` 再存一份 | +10.69 MB | `pk4` − `lower` |
| 为 `word_lower` 额外维护的二级索引（含 rowid） | +17.84 MB | `cur2` − `pk4` |
| 从未被读取的 `record_size` | +2.91 MB | `cur` − `cur2` |
| 合计 | ≈51.55 MB | `cur` |

即：**约 1/3 是词头本身、1/3 是小写副本、1/3 是重复的二级索引**。正文完全不占索引空间。

### 4.3 各路线对比（富文本 1M）

| 路线 | 索引体积 | 建索引 | 精确 p50/p95 | 前缀 p50/p95 | 模式 p50/p95 | 峰值工作集 |
|---|---|---|---|---|---|---|
| A 现方案 | 51.55 MB | 2816 ms（同 `cur` 变体） | 0.54 / 1.01 | 1.05 / 2.21 | 8.05 / 15.71 | 62.0 MB |
| C1 `cur2`（删 `record_size`） | 48.64 MB | 2337 ms | 0.50 / 1.27 | 1.12 / 2.29 | 10.18 / 16.34 | 58.3 MB |
| C2 `pk4`（`WITHOUT ROWID`，PK(`word_lower`,`word`)） | **30.80 MB** | 2788 ms | 0.47 / 1.00 | 0.86 / 1.88 | 8.15 / 12.25 | 58.3 MB |
| C2' `pkoff`（同上，主键再加 `record_offset`，允许重复词头） | **30.80 MB** | 2339 ms | 0.46 / 0.71 | 0.81 / 1.22 | 6.18 / 10.25 | 61.8 MB |
| C3 `pk8`（同上，页 8KB） | 30.81 MB | 2462 ms | 0.69 / 1.21 | 0.95 / 1.69 | 6.55 / 10.65 | 58.3 MB |
| C4 `pk16`（同上，页 16KB） | 30.83 MB | 2542 ms | 0.52 / 1.01 | 0.92 / 1.70 | 6.73 / 12.40 | 62.0 MB |
| C5 `lower`（只存小写词头，丢失原始大小写） | 20.11 MB | 2391 ms | 0.49 / 0.98 | 0.84 / 1.32 | 5.99 / 10.95 | 62.0 MB |
| B 直接用 mdx 键索引 | 0（不落盘） | 打开 6 ms | 1.16 / 2.29 | 0.90 / 1.76 | 7.46 / 38.59 | 45.2 MB |
| D zstd 分块索引 | **6.10 MB** | 2841 ms | 0.28 / **0.59** | 0.74 / 1.72 | 30.12 / 53.15 | 140.4 MB |

简明样本（正文 84.4MB / mdx 29.7MB）的补充测量：

| 路线 | 索引体积 | 建索引 | 精确 p50/p95 | 前缀 p50/p95 | 模式 p50/p95 | 峰值工作集 |
|---|---|---|---|---|---|---|
| A 现方案 | 50.63 MB | 3164 ms（端到端） | 0.55 / 0.99 | 0.90 / 1.98 | 8.24 / 16.05 | 59.4 MB |
| B mdx 键索引 | 0 | 打开 3 ms | 1.80 / 3.84 | 0.76 / 1.91 | 13.90 / 43.85 | 44.0 MB |
| D zstd 分块 | 5.60 MB | 3454 ms | 0.32 / 0.50 | 0.65 / 1.29 | 27.77 / 45.35 | 133.2 MB |

C 组在简明样本上没有重跑：索引只由词头决定，两样本词头集合完全相同（同为 100 万条、9.75MB 词头文本），索引体积必然一致；正文更短只会让精确查询略快。

路线实现要点：

- **B（mdx 键索引直查）**：解析 mdx 键区索引，把每块的"首词"常驻内存（279 块、约 5.4KB），精确/前缀二分定位到块后解压该块（≤64KB）线性扫描，模式查询扫描全部键块。磁盘零增量、内存最低。**但见 4.4：语义不等价。**
- **C（SQLite 变体）**：只改表结构与查询 SQL。`WITHOUT ROWID` 复合主键把"表 + 二级索引"合并成一份 B 树；页大小 4/8/16KB 对体积和延迟均无可测差异；SQLite 没有列级压缩，靠"少存冗余"取胜。
- **D（zstd 分块索引）**：词头按小写排序，每 512 条一块，块内前缀编码（公共前缀长度 + 后缀 + 记录偏移增量 + 大小写差异标记），整块 zstd（level 12）压缩；文件末尾存"首词/末词/偏移/长度"索引供二分。精确/前缀查询解压 1~2 块（约 5~7KB 解压后），模式查询解压全部 1954 块（约 10MB）。

### 4.4 正确性校验（重要）

以"从 mdx 全量词条构建的内存字典/列表"为真值，对比原型的返回集合（简明样本，1M 词条）：

| 校验项 | B（mdx 键索引） | D（zstd 分块） |
|---|---|---|
| 精确 300 词 | **失配 131** | 失配 0 |
| 前缀 200 词 | **失配 152** | 失配 0 |
| 模式 `app*` / `*ing` / `?a?e` | 1071/29093/327，全部一致 | 1071/29093/327，全部一致 |

B 的失配根因：mdx 键块按**字节序**排序，大写字母排在小写之前（`B`=0x42 < `a`=0x61），而现有产品语义是大小写不敏感（`word_lower`）。基于字节序的二分找不到大小写混合的词（例：`badiner` 实际在第 65 块，二分定位到第 4 块）。这不是原型实现缺陷，而是 mdx 键序本身不支持大小写折叠——除非接受"大小写敏感查询"或再加一份归一化索引（那就回到 C/D 的成本）。

D 的排序键就是小写形式，因此与现有语义一致，三类查询全部一致。

## 5. 阈值与判定

这些阈值属于产品决策，下面是建议值（括号内为当前基线），可按需调整：

| 编号 | 指标 | 建议阈值 | 依据 |
|---|---|---|---|
| T1 | 精确查询 p95 | ≤ 1.5 ms（现 1.0） | 不低于现有体验，留 50% 余量 |
| T2 | 前缀查询 p95 | ≤ 5 ms（现 2.2） | 输入联想需即时 |
| T3 | 模式查询 p95 | ≤ 100 ms（现 16） | 用户显式触发，可接受一次明显停顿 |
| T4 | 1M 词条导入 | ≤ 10 s（现 3.5） | 一次性操作，10s 内不显著打断 |
| T5 | 导入峰值工作集 | ≤ 200 MB（现 62） | 桌面应用可接受上限 |
| T6 | 索引体积 | ≤ 1.0 × mdx（且越小越好） | "不显著超过原 mdx" |

逐项判定（以更不利的简明样本为准）：

| 路线 | T1 精确 | T2 前缀 | T3 模式 | T4 导入 | T5 内存 | T6 体积 | 总体 |
|---|---|---|---|---|---|---|---|
| A 现方案 | 通过 0.99 | 通过 1.98 | 通过 16.05 | 通过 3.16s | 通过 59.4 | **不通过 50.63MB = 1.70×** | 不通过 |
| B mdx 键索引 | **不通过 3.84** | 通过 1.91 | 通过 43.85 | 通过（复制+3ms） | 通过 44.0 | 通过 0 | 不通过（且语义不等价） |
| C2' `pkoff` | 通过 0.71 | 通过 1.22 | 通过 10.25 | 通过 2.34s | 通过 61.8 | 勉强（30.80MB = 1.04×） | 基本通过 |
| D zstd 分块 | 通过 0.50 | 通过 1.29 | 通过 45.35 | 通过 3.45s | 通过 133.2 | 通过 5.60MB = 0.19× | 通过 |

补充：A 在富文本样本上 T6 通过（0.40×），所以"现方案不可接受"只发生在**正文很短、词头很长的词典**（简明/词表型），这正是上一轮 30 万词条 bench 暴露的场景；正文丰富的词典索引占比本来就不高。

## 6. 结论与建议

### 6.1 推荐路线

**第一步（已实现，2026-11-10）：C2' —— 只改 SQLite schema。**
- 表改为 `CREATE TABLE words (word TEXT NOT NULL, word_lower TEXT NOT NULL, record_offset INTEGER NOT NULL, PRIMARY KEY (word_lower, word, record_offset)) WITHOUT ROWID;`，删除从未使用的 `record_size`，删除独立的 `idx_words_lower`。
- 主键带 `record_offset` 是为了兼容"同一词头多条记录"的 mdx（原 schema 允许重复，若只用 `(word_lower, word)` 做主键，遇到重复词头会在导入时约束冲突）；实测带偏移的复合主键体积与延迟和不带偏移的版本相同（30.80MB）。
- 体积 51.55 → 30.80MB（−40%），精确/前缀/模式延迟与内存均无退化（差异在噪声范围内）。
- 改动面：`MdxIndexDatabase.Build` 建表/插入 SQL、`MdxDictionaryStore` 的版本检测与后台重建；`MdxSource` 查询 SQL 与 `MdxReader` 记录读取路径均未改动。
- 索引版本写入 SQLite `user_version`（当前为 2）。`CreateSources` 打开词库时检测到旧版本会在后台用已有 mdx 副本重建，用户无需删除或重新导入；重建失败时保留旧索引继续查询（仅体积偏大），记录到 Trace，下次打开再试。
- 落地后的复测数据见第 8 节。

**第二步（可选，取决于体积目标）：D —— zstd 分块索引。**
- 索引 30.80 → 6.10MB（相对现方案 −88%，简明样本 0.19× mdx），精确查询 p95 从 1.0ms 降到 0.59ms，前缀持平，模式查询 45~53ms（现 16ms，仍满足 T3）。
- 改动面：新增索引构建器 + 读取器（原型约 600 行：变长整数、前缀编码、块索引、zstd 依赖 `ZstdSharp.Port`）、`MdxSource` 改为走新读取器、模式查询的正则翻译、导入进度与取消。
- 工作量级：3~5 天（含单测、损坏文件容错、旧索引迁移）。
- 风险：自建二进制格式（格式版本、截断/损坏处理）；导入峰值内存 133~140MB（因内存中排序 100 万条；可改为分块外排降到 ~70MB，但增加复杂度）；模式查询退化为全量解压扫描（词条再翻倍会到 ~90ms，需观察）；zstd 引入一个第三方依赖（纯托管实现，体积小）。
- 建议：如果产品能接受"索引约为 mdx 的 1 倍（简明词典）/ 0.24 倍（富文本词典）"，**只做 C2**；如果要求索引必须显著小于 mdx（例如 ≤0.5×），再做 D。

**不建议 B（mdx 键索引直查）作为主路线**：虽然零额外存储、内存最低，但它无法在字节序键上实现大小写不敏感查询（精确失配 43%、前缀失配 76%）。若未来要做"未导入词库的快速预览"，B 可作为只读、大小写敏感的临时通道单独评估。

### 6.2 对现有 mdx 窄范围实现的影响

- `MdxReader` 与记录读取路径完全不变（C/D 都只替换 sidecar 的存储与查询）。
- 支持范围不变：仍只支持未加密 + zlib/无压缩 + UTF-8/UTF-16 的 mdx 2.0；加密/LZO/1.2/GBK 依旧拒绝。
- 索引结构版本已落地（SQLite `user_version` = 2），旧索引在打开词库时后台重建，失败保留旧索引可继续查询。
- 删除/停用/恢复语义不变（索引文件仍是可删除的派生数据，重建即可）。

### 6.3 与"上一轮 300k bench"的差异说明

上一轮样本正文短（每条约几十字节）且高度重复，词头平均 15 字符，导致"索引 ≈ 文本"；本轮用 100 万条真实释义 + 随机化标记复测后，正文与索引的比值取决于词典类型：富文本 760.7MB 正文 / 51.6MB 索引（1:14.8），简明 84.4MB / 50.6MB（1:0.6）。**索引只与词头相关，这一点在两条样本间一致。**

## 7. 未测与限制

- 单机、单次测量；文件缓存为热态，未测冷启动/磁盘 IO 争用；p95 波动约 ±20%，毫秒级差异不可过度解读。
- 生成样本来自 ECDICT 的英文词条，未覆盖中文词头、非 BMP 字符、UTF-16 mdx、超大单条记录（数 MB 的图片型释义）；这些场景索引行为可外推，但未实测。
- 模式查询只测了 `app*`、`*ing`、`?a?e` 三种形态；`%x%` 这类无前缀的 `LIKE` 在全路线都是全表扫描，未单独展开。
- 原型代码为验证性质（未做参数校验、损坏恢复、并发、取消），不作为交付实现；D 的构建内存优化（外排）只做了判断，未实现验证。

## 8. C 方案落地结果（已实现）

实现改动：

- `MdxIndexDatabase`：表改为 `WITHOUT ROWID` + `PRIMARY KEY(word_lower, word, record_offset)`，删除 `record_size` 与独立的 `idx_words_lower` 索引；建库先写 `{index}.tmp` 再原子替换目标文件，中途失败只清理临时文件、不破坏原有索引；写入 `PRAGMA user_version = 2`。
- `MdxDictionaryStore`：`CreateSources` 打开词库时用 `IsCurrent` 检测版本，旧版本在后台（`Task.Run`，按词库 id 去重）用已有 mdx 副本重建；提供 `RebuildIndexAsync` 供显式重建；重建异常只写 Trace，旧索引保留、查询照常，下次打开再试。
- `MdxSource` 与 `MdxReader` 未改动：索引只用于定位 `record_offset`，正文仍从 mdx 压缩块按需解压。

复测（同一台机器、同一批样本、同一口径；对照第 4 节的 A/C 数据）：

| 样本 | 导入 | mdx | 索引 | 合计占用 | 精确 p50/p95 | 前缀 p50/p95 | 模式 p50/p95 | 峰值工作集 |
|---|---|---|---|---|---|---|---|---|
| 富文本 1M（第 1 次） | 3442 ms | 129.28 MB | **30.80 MB** | 160.08 MB | 0.54 / 1.58 | 1.09 / 2.35 | 7.99 / 15.95 | 62.8 MB |
| 富文本 1M（第 2 次） | 3464 ms | 129.28 MB | **30.80 MB** | 160.08 MB | 0.66 / 1.35 | 1.35 / 2.37 | 9.23 / 22.05 | 63.1 MB |

对照结论：

- **体积达到预期**：51.55 → 30.80MB（富文本，−40.3%），50.63 → 30.72MB（简明，−39.3%），与调研中 C 变体的 30.80MB 一致；简明词典下索引从 1.70× mdx 降到 1.03×。
- **延迟未退化**：精确 p50 0.53~0.66ms、p95 1.05~1.58ms（原方案 0.99~1.01ms p95），前缀 p95 2.08~2.37ms（原 1.98~2.21ms），模式 p95 15.95~22.05ms（原 16.05ms）；差异在 ±20% 噪声内，富文本第一次的精确 p95 偏高属于抖动（同一变体两次 1.58/1.35）。
- **导入耗时基本持平**：3442/3464ms 与 3343ms，原方案为 3545/3164ms。
- **峰值内存持平**：60.6~63.1MB，原方案 59.4~62.0MB。
- 行为契约未变：大小写不敏感精确/前缀、`WordPattern` 模式查询、多源去重与排序均复用原查询路径；单测新增"索引结构/版本号""旧版本索引重建""后台自动重建""重建失败保留旧索引""同一词头多条记录"五项，其余既有用例期望值未改动。

已知行为（不是缺陷，但需要知道）：

- 升级后**第一次打开**词库时用的仍是旧索引（体积暂时偏大），后台重建完成后体积才降下来；重建期间查询不受影响。
- 重建会写 `{index}.db.tmp` 后原子替换；若替换瞬间恰好有查询占用索引文件，替换最多重试 4 次（约 300ms），仍失败则保留旧索引、下次启动重试。
- 重建进度只写 Trace，未接入导入界面的进度条（重建发生在启动后台，不阻塞 UI）。

发布目录实跑（2026-11-10，用 Release 发布产物，非源码工程）：

- 用发布目录的 `Flint3.Data.dll`/`Flint3.Core.dll` 跑完整链路：导入（205 词条）→ 精确/前缀/模式查询 6 项全通过（含大小写混合 `FLINT`/`flint` 命中 `Flint`）→ 把索引 `user_version` 改为 0 模拟旧索引后重新打开，查询立即可用、208ms 内后台重建回 2 → 停用后查询源为 0 → 删除后 mdx/索引文件均移除、配置为空。
- 直接启动发布版 `Flint3.exe`（免打包）验证界面：输入仅存在于 mdx 的词条时展示 mdx 正文；精确、前缀、通配符模式三类输入均能正常出结果。
- 附带确认一个既有（与本次改动无关）的语法边界：`WordPattern` 只接受 ASCII 字母与通配符，含数字的模式（如 `smokeword00?`）会被判定为非模式、回退普通查词，因此这类输入查不到结果；调研阶段用的 `app*`/`*ing`/`?a?e` 不受影响。
